## 七、你问的那个真问题：GPT 一天，胜过我们一百多批吗

### 部分为真，但把它读成「换个模型就行」会错

四闸的每一闸，都是对一个**已经发生过的具体失败**的命名：

| 闸 | 它命名的是哪一次失败 | 那次失败是谁在哪批查出来的 |
|---|---|---|
| GATE_1 取证半径 | §214「其中必有错乱，故不释」在条文后约 400 字 | **用户人读**（125批） |
| GATE_2 词-义双轨 | 「胃气」实有 740 处；`脉缓` 漏掉「脉逐渐缓」 | 上级复核 125批 |
| GATE_3 原子化 | 缓→中风（证型 vs 病因）；数→热 五谓词 | 123–125批之具体格 |
| GATE_4 归因 | C卷 speaker uncertain；十二书体例 | 125批 卷首实查 |

⇒ 准确的说法是：**GPT 用一天，把一百多批积累的、带锚的、可复核的具体失败，抽象成了四个名字。**
它能做到，是因为**这些失败已经被摆在桌面上、逐条编号、带锚**。

**但这不能拿来给我们开脱。真正该问的是：为什么一百二十批没人做这一步抽象？**

### 答案很具体，而且是结构性的

三方分工里，**没有任何一方的职责是「把过去 N 批的错误归类」**：

```
用户   提方向、给临床判断、人读原著
上级   形式化、提裁决、复核
Code   取证、挂载、自查、报告
```

**自查只能抓「本批的错」。它在结构上抓不到「错的类」。**
我每批末尾都写「未做」，然后开下一批；错误被逐条修复，**从未被逐类命名**。
一百二十批里，「取证半径太小」发生了**三次**，我三次都写了「已改」——
**第三次的时候才由上级说出「这是第三次」。**

⇒ 所以结论不是「主线该搬去 GPT 那边」，是：
> **必须有一方的常设职责是跨批抽象。这个岗位空了一百二十批。**

这也是我在第三节把 `hxs-postmortem` 排在首位的原因。**四闸是产物，空岗才是病灶。**

### 我该反思的，具体是这三条

1. **我把「本批已改」当成了修复。** 修复的单位应该是**类**，不是条。
2. **我用产量代替了判断。** 126 批、97 个工具、81 个 term_layer 文件、56 份报告——
   体量本身从未被我当作一个需要解释的现象。
3. **我沿着自己的总结往下推。** 125批 上级那句「**我重新按原始资料核了一遍，而不是沿着 Code 的总结往下推**」——
   这句话的另一面是：**我一直在沿着自己的总结往下推**，而且没意识到。

## 八、三方的长短，我照实写（请把这一节转给上级线）

### 记忆

| 方 | 记忆形态 | 失效方式 |
|---|---|---|
| **GPT** | 无持久记忆 | **可见的失忆**——你每次要重新交代，所以你会去补 |
| **上级线（claude.ai 长对话）** | 一条对话攒一百多批 | 上下文满了会被**摘要**；摘要保留结论、丢掉证据与限定词 |
| **我（Code）** | 上下文同样会被摘要；**但仓库是持久的** | **不可见的失忆**——摘要静默替换来源，没人会去补 |

⛔ **要点：我和上级线的记忆病和 GPT 是同一种，只是被伪装得更好。**
GPT 的失忆是**可见**的，所以会被补救；我们的失忆是**不可见**的，所以不会。

## 九、你问「是不是对话太长影响了严谨性」——是，而且机制可写出来

不是「累了」。机制是这样的，**而且上面三个实例就是它的产物**：

```
① 上下文填满
② 早期轮次被压缩成摘要
③ 摘要保留【结论】，丢弃【证据】与【限定词】
④ 后续推理建在失去限定词的结论上
⑤ ⇒ 假说硬化成事实（C卷同族）；幽灵对象获得引用（63组）
```

还有第二个机制，更隐蔽：**长对话会让「重读原始材料」的相对成本变高**——
因为「我们已经讨论过了」。于是默认走总结。
125批 上级那句自述之所以有价值，是因为它**明确拒绝了这个默认**。

### ⇒ 补救是架构性的，不是意志性的

| 做法 | 为什么有效 |
|---|---|
| **持久状态只认仓库文件，且必须带锚** | 文件不会被摘要 |
| **每一方每批从文件重新推导，不从对话** | 切断 ③→④ |
| **上级线接上仓库**（§一 三条路） | 它才可能做「从文件推导」 |
| **交接包由脚本生成，不由人转述** | 转述丢限定词；脚本不丢 |
| `hxs-reading` 的「读毕报三数」 | 把「我读了多少」变成必须报的数 |

⛔ 并请注意一个反直觉的推论：
**换新对话会让上级线失去连续性，但同时让它失去「沿总结往下推」的惯性。**
在它能读仓库之后，**连续性可以由仓库提供，而不必由对话提供**——
那时开新对话的代价会大幅下降。**这是把连续性从对话迁到资产的关键一步。**
