## 三、所以我认为“16,914行还不够用”不是正确的问题  
真正的问题是：  
**16,914行里面，哪些东西是“知识”，哪些是“判据”，哪些是“执行算法”，哪些是“历史”，哪些是“测试资产”，哪些是“案例答案”？没有彻底分离。**  
现在至少混了六种东西：  
**A. 原始知识**  
仲景原文、胡老解释、按语、医案。  
**B. 结构化知识**  
例如：  
太阳＝表阳 少阴＝表阴 阳明＝里阳 太阴＝里阴……  
**C. 执行规则**  
例如：  
未采≠阴性。  
**D. 元规则**  
例如：

**E. 历史修正记录**  
例如：  
㊴批错了什么、㊵批撤了什么、㊿批又修正什么。  
**F. 测试资产**  
G1-G16、W-1错案、W-2正例、历史通过率。  
这六种东西**不能放在同一个执行上下文中让LLM自己决定优先级**。

## 六、为什么会“挂载了却用不上”？  
我现在认为至少有 **5个根因**。  
   
⸻  
   
## 根因1：没有真正的“执行调度器”  
现在是：  
```
病例
 ↓
LLM读16,914行
 ↓
自己决定哪些R相关
 ↓
自己组合
 ↓
输出

```
这实际上不是引擎。  
这是：  
**一个超长提示词。**  
真正的引擎应该是：  
```
病例
 ↓
输入解析
 ↓
调用【病位模块】
 ↓
调用【病性模块】
 ↓
调用【时间模块】
 ↓
调用【方证模块】
 ↓
调用【反证模块】
 ↓
调用【安全模块】
 ↓
输出

```
每一步只允许访问它自己的数据域。  
   
⸻  
   
## 七、根因2：我们把“防止过度排除”做过头了  
这是另一个非常核心的问题。  
现在：  
六经全部预设存活； 只有本经反义才能排除； 没被排除的全部保留。  
 hxs_engine_v79_full 20.md  
这个规则解决了过去的一个错误：  
过度收窄。  
这是对的。  
但是它后来产生了另一个问题：  
**“没有证据支持”与“没有证据排除”之间失去了足够的区分。**  
例如：  
```
候选A
有正面证据
无反证

候选B
没有正面证据
也没有反证

```
当前模型容易把：  
```
A ≈ B

```
因为两者都“没有被排除”。  
但实际上应该是：  
```
A = 有支持
B = 未证实

```
这就是：  
**“幸存”不能等于“成立”。**  
当前引擎已经部分意识到了这一点，例如R25规定少阳不能只因为提纲缺失而排除，但又要求表里排除后才能通过残余法进入半表半里。  
 hxs_engine_v79_full 20.md  
但是这个原则还没有被提升成整个系统统一的**证据状态机**。  
   
⸻  
   
## 八、根因3：我们把“症状→病位”做成了过大的映射表  
这里其实已经走到一个很重要的正确结论：  
当前引擎自己经过实测发现：  
胡老很少直接说“某症属于某病位”。  
真正明确的只有少量，例如：  
* 下利属于里；  
* 小便清者知不在里仍在表；  
* 四肢逆厥反映于里；  
* 某些身痛、脉紧等与表有关。  
而不是存在一个巨大的：  
```
症状 → 病位

```
字典。  
当前引擎自己已经承认，显式症状→病位只有少量原文锚，不能用统计共现替代。  
 hxs_engine_v79_full 20.md  
这实际上非常重要。  
因为胡老真正使用的是：  
**整体证候反应 → 判断病邪集中反应在哪里**  
而不是：  
300个症状逐个贴病位标签。  
所以这里应该**删掉大量伪精确映射**，而不是继续补。  
   
⸻

这也是110批、111批暴露出来的问题。  
当前引擎自己已经经历了：

**“★到底是什么”没有真正从胡老原文中被完整定义出来，我们一直在给一个人类自然语言中的“辨证要点”强行设计数学身份。**  
引擎自己也承认：  
胡老没有建立“★类型学”，这是我们给他没有提出的问题造答案。  
 hxs_engine_v79_full 20.md  
我认为这一点应该进一步贯彻：  
**不要再试图建立一个统一的“★数学理论”。**

**不能为了可计算性而强行让所有方证具有同一形式。**

## 十、根因5：我们已经开始出现“为了可计算而创造不存在的变量”  
这是我认为最危险的一条。  
例如现在的：

这些数字在引擎里自己已经明确标为：  
[推演]，非胡老原文。  
 hxs_engine_v79_full 20.md  
问题不在于“能不能打分”。  
问题是：  
**我们没有证明这些数字能够代表辨证中的证据强度。**  
于是出现：  
```

+
人工设计分数
=

```
但35%没有真实统计意义。  
所以：  
**数字化 ≠ 可计算性。**  
**真正的可计算性是状态可判定、证据来源明确、规则可复现，而不是给每条证据发一个百分比。**  
这一点我建议直接大幅收缩，甚至删除。


**“全量挂载”与“全量同时阅读”不是一回事。**

## 二十八、然后重新定义“引擎是否成功”  
不再用：  
规则条数 挂载次数 prompt长度 单次通过率  
作为核心指标。  
至少要有：  
**1. 独立复现率**  
同一病例：  
```
不同实例
不同时间
不同上下文

```
结果是否一致。  
**2. 遮答案准确率**  
病例必须：  
```
去掉：
证属
方名
治疗结果
作者结论

```
再执行。  
**3. 反例鲁棒性**  
专门攻击：  
```
单症状
主观热感
同症异证
合病
并病
多义词
治疗史
未来信息污染

```
**4. 未知纪律**  
专门测试：  
没问的东西是否被错误当成“无”。  
**5. 可追溯性**  
任何最终判断都能回溯：  
```
病例事实
→ 证象
→ 判据
→ 原文
→ 六经
→ 方证
→ 排除项

```
**6. 反事实稳定性**  
改变一个关键事实：  
```
如果“有汗”→无汗
如果“口苦”→无口苦
如果“便溏”→便硬

```
系统是否按照原文真正发生预期变化。  
这比“总体准确率98%”有价值得多。
