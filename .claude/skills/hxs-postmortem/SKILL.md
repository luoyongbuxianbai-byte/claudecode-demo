# 跨批错误归类（hxs-postmortem）

## 这个 skill 存在的理由

一百二十批里，**没有任何一方的职责是「把过去 N 批的错误归类」**：

```
用户   提方向、给临床判断、人读原著
上级   形式化、提裁决、复核
Code   取证、挂载、自查、报告
```

**自查倾向于只抓「本批的错」，历史上也确实没抓到过「错的类」。**
⚠ 但这是**观察到的失效模式，不是定理**——不得写成「自查在结构上不可能发现错误类」。
每批末尾写「未做」，然后开下一批；错误被逐条修复，**从未被逐类命名**。

| 类 | 发生次数 | 每次的处理 | 何时才被命名 |
|---|---:|---|---|
| 取证半径太小 | **3** | 「已改」 | 第三次由上级说出「这是第三次」 |
| 测试断言写在错误对象上 | **5** | 「已改」 | ⛔ **至今未立为协议** |
| 从局部证据得全称否定 | ≥3（A2/A3/E） | 「已改」 | 126C–126E |

⇒ 126批 之四闸（GATE_1–4），**是一次迟到一百二十批的归类**。
它能被做出来，是因为失败已经逐条编号、带锚、摆在桌面上——
**材料一直在，缺的是「有人专门去做这一步」。**

⛔ 所以本 skill 的核心不是「反思」，是**一个必须产出新行的表**：
`rules/failure_classes_v0.json` 的 `classes` 数组。
**跑完一次归类而该数组一行没动，要么是真的没有新类，要么是这次归类没做。区别要说清楚。**
⛔ **不设新增类配额。** 复用既有类、判定无新类、修正既有分类，**三者同样是有效产出**。

## 规程

### 第一步：把材料摊开，不许凭印象

```bash
# 最近 N 批报告里，所有自承的错误
grep -n "⛔\|我的错\|订正\|撤回\|作废\|误判\|失准" reports/报告_第12*.md
# 上级／用户的驳回
ls 指令/
# 现行已立之类
python3 -c "import json;d=json.load(open('rules/failure_classes_v0.json'));[print(c['id'],c['name']) for c in d['classes']]"
```

⛔ **不得带截断参数**（A2）。这里要的是全集，不是样例。

### 第二步：逐条填一张表——**先写事实，后写归类**

| 批 | 错了什么 | 谁发现的 | 当时怎么处理的 | 触发条件 |
|---|---|---|---|---|

「谁发现的」这一栏最有信息量。**如果一类错误从来不是自查发现的，
那说明自查对它是盲的**——那本身就是一个要立的类。

「触发条件」写**可复现的机制**，不写「疏忽」。
`grep … | head -10` 是机制；「不够仔细」不是。

### 第三步：聚类，并对每个候选类问四个问题

1. **它发生过几次？** 一次 ⇒ 个案；≥2 且触发条件相同 ⇒ 候选类。
2. **现有的类盖得住吗？** 盖得住就不要新立——
   ⚠ 但要小心反向：126C 发现 `not_auditable_missing_anchor` 一名**混了两件事**。
   **判据是：该类下所有成员的修复动作是否相同？不同即须拆。**
3. **它的修复动作是什么？** 说不出修复动作的类，不是类，是抱怨。
4. **现有的闸盖得住吗？** 盖不住就明写「本类现无闸」——
   A2 就是这么被发现的：**四闸都只盖读原文，没盖读工具输出。**

### 第四步：写进登记，并给出处

新类必须带：`id`／`name`／`def`／`instance`（带锚或批次）／`gate`／`rule`／`proposed_by`／`status`。

⛔ 依协议14，**新立之类须经复核方可生效**；本 skill 只负责提出与登记 `status: proposed`。

### 第五步：报三个数

```
本次归类覆盖：第 __ – __ 批
检出错误条目：__ 条
新立类：__ 个｜并入既有类：__ 条｜判为个案：__ 条
```

⛔ 三数都要报。只报「新立 0 个」而不报覆盖区间，等于没做。

## 两个反模式

**反模式一：把归类写成检讨。**
「我应该更仔细」不是类。**类是一个带触发条件、可被别人复现的机制。**

**反模式二：归类之后接着干活，不改流程。**
一个类如果没有对应的闸、测试或 skill 条款，它下次还会发生。
⇒ 每立一个类，必须同时回答：**「下次它再发生时，什么东西会先变红？」**
答不出来 ⇒ 该类记 `no_detector`，进待办，**不算已治**。

## 谁来做

⛔ **不应由「产生错误的同一执行者」独任。**
理由不是主观信任，是可观察的失效模式：
本工程的类，**没有一个是由犯错那一方自查命名的**——
GATE_1 由用户人读逼出，GATE_2/3/4 由上级复核逼出，F 类由用户举「阳五型」逼出。

⇒ 现行分派（126E 上级令）：**跨批归类交 GPT 线**；
**Code 负责提供机器可枚举之错案资产**——即第一步那几条命令能跑出东西来，
且 `rules/failure_classes_v0.json` 始终是最新的。
